# Technical components that could upgrade stream2clip (state as of November 2026)

Scope: models, libraries and methods that run locally on a consumer Windows PC, checked for license fit with an MIT project. Every license below is what the model card or repo says. Where sources conflict, both are given. "Weights license" matters even when the code is MIT, because stream2clip users who run monetized clip channels count as commercial users.

## 1. Highlight detection: multimodal/video-language models, moment retrieval, audio events, chat research, datasets

### Takeaway
No public model or benchmark targets VTuber or live-stream clipping on a consumer PC. The practical upgrade is to keep the chat/loudness z-score core and add two cheap, permissively licensed signals: an AudioSet audio tagger (EfficientAT MIT, PANNs CC-BY-4.0) for laughter, screams and applause, and a small Apache-2.0 VLM (Qwen3-VL 2B/4B/8B, SmolVLM2) that only re-ranks or describes the top candidates. Academic moment-retrieval models (QVHighlights SOTA) are tuned for query-driven retrieval on short clips, and the only large live-stream highlight dataset with chat (KLive) is from Kuaishou.

### Cited Findings

**Moment retrieval / highlight detection (QVHighlights family)**
- CoSTL (arXiv 2606.01149, submitted 31 May 2026) claims to beat the previous SOTA, UVCOM, on QVHighlights, Charades-STA, TACoS and TVSum. This is the authors' own claim. No independent leaderboard confirmed it — [arXiv 2606.01149](https://arxiv.org/abs/2606.01149)
- Saliency-Guided DETR (arXiv 2410.01615, revised Feb 2026) reports 58.8 mAP on QVHighlights and introduces the InterVid-MR pretraining dataset — [arXiv 2410.01615](https://arxiv.org/html/2410.01615v2)
- VideoLights (arXiv 2412.01558) claims SOTA on QVHighlights, TVSum and Charades-STA, with average gains of 4.29%, 1.98% and 0.7% — [arXiv 2412.01558](https://arxiv.org/pdf/2412.01558)
- "Moment and Highlight Detection via MLLM Frame Segmentation" (arXiv 2512.12246, Dec 2025) applies segmentation objectives to MLLM output tokens. It reports 56.74 HIT@1 on QVHighlights using only 25 frames, so it is an efficiency-oriented MLLM approach — [arXiv 2512.12246](https://arxiv.org/abs/2512.12246v1)
- SVHighlights (arXiv 2606.06926) targets "extremely long" sport-video highlight detection. Long input is closer to the stream setting than QVHighlights, but it is sports content. I saw only the title — [arXiv 2606.06926](https://arxiv.org/pdf/2606.06926)

**Video-language models usable locally**
- Qwen3-VL family: dense 2B, 4B, 8B and 32B plus MoE variants, trained with up to 256K context. The tech report says it moved from T-RoPE to "explicit textual timestamp alignment for more precise temporal grounding" — [Qwen3-VL tech report, arXiv 2511.21631](https://arxiv.org/abs/2511.21631v1)
- The Qwen3-VL-4B-Instruct card gives license **Apache-2.0**, "Native 256K context, expandable to 1M", hours-long video with second-level indexing, "Text–Timestamp Alignment" for event localization, and OCR in 32 languages (the list is not given on the card). It points to GGUF quantizations for llama.cpp, Ollama and LM Studio, plus vLLM and SGLang. It gives no VRAM figure — [HF: Qwen/Qwen3-VL-4B-Instruct](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct)
- Qwen publishes official GGUF builds (e.g. Qwen3-VL-8B-Thinking-GGUF) that run through `llama-mtmd-cli` / `llama-server` with a separate mmproj file — [HF: Qwen3-VL-8B-Thinking-GGUF](https://huggingface.co/Qwen/Qwen3-VL-8B-Thinking-GGUF). llama.cpp is MIT-licensed — [Wikipedia: llama.cpp](https://en.wikipedia.org/wiki/Llama.cpp). Its multimodal library libmtmd is described as "under very heavy development" with breaking changes expected — [llama.cpp mtmd README (Debian mirror)](https://sources.debian.org/src/llama.cpp/8064%2Bdfsg-1/tools/mtmd/README.md); [llama.cpp multimodal docs](https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md)
- A Nov 2025 LM Studio bug report describes Qwen3-VL image input failing in a llama.cpp backend, so backend builds vary — [LM Studio issue #1176](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/1176)
- Small Qwen3-VL models are weak at zero-shot temporal grounding. With 16 frames, 2B/4B/8B scored 0.13/0.15/0.21 on one grounding metric and near zero on spatial grounding — [arXiv 2607.24570](https://arxiv.org/pdf/2607.24570)
- TimeLens2 (July 2026) fine-tunes Qwen3-VL 2B/4B/8B for grounding, with gains of +14.2/+13.0/+18.1 mIoU over the backbones. This is a third-party fine-tune — [TimeLens2, arXiv 2607.17423](https://huggingface.co/papers/2607.17423.md)
- SmolVLM2 (256M / 500M / 2.2B) is **Apache 2.0**. ggml-org publishes video GGUFs, and llama.cpp takes video "as a sequence of images" — [HF blog: SmolVLM2](https://huggingface.co/blog/smolvlm2); [ggml-org SmolVLM GGUF collection](https://huggingface.co/collections/ggml-org/smolvlm-gguf); [ggml-org/SmolVLM2-500M-Video-Instruct-GGUF](https://huggingface.co/ggml-org/SmolVLM2-500M-Video-Instruct-GGUF)
- InternVideo2.5-Chat-8B: the card metadata says **Apache-2.0**. It reports MVBench 75.7, LongVideoBench 60.6, VideoMME (no subs) 65.1, MLVU 72.8 and LVBench 46.4, and handles video at least 6x longer than its base via HiCo token compression — [HF README (blame view)](https://huggingface.co/OpenGVLab/InternVideo2_5_Chat_8B/blame/main/README.md); [arXiv 2501.12386](https://arxiv.org/abs/2501.12386)
- Qwen3-Omni-30B-A3B (Instruct / Thinking / Captioner) is **Apache 2.0**. Instruct accepts audio+video+text. The Captioner is audio-only, takes one clip of ≤30 s per call and accepts no text prompt. A community AWQ 4-bit build exists, but no official VRAM figure was found — [Qwen3-Omni tech report, arXiv 2509.17765](https://arxiv.org/html/2509.17765v1); [HF: Qwen3-Omni-30B-A3B-Captioner](https://huggingface.co/Qwen/Qwen3-Omni-30B-A3B-Captioner); [HF: AWQ 4-bit build](https://huggingface.co/cpatonn/Qwen3-Omni-30B-A3B-Instruct-AWQ-4bit)
- Gemma 4 (2 Apr 2026) is **Apache 2.0**, replacing the earlier restrictive Gemma terms. Sizes are E2B, E4B, 26B MoE and 31B dense. The 4-bit 31B reportedly runs on an RTX 4090 / RX 7900 XTX — [The Next Web](https://thenextweb.com/news/google-gemma-4-open-models-apache-2-launch); [eWeek](https://www.eweek.com/news/google-gemma-4-apache-2-open-models/); [9to5Google](https://9to5google.com/2026/04/02/google-gemma-4/)

**Live-stream highlight research and datasets**
- KLive (Kuaishou, ICME 2024, arXiv 2407.12002): 17,897 live rooms / 19,334 hours, with visual frames, comments and ASR per segment and dense (non-binary) annotations. The model uses only look-back windows (causal), adds a Modality Temporal Alignment Module for misaligned chat/audio/video, and uses a Border-Aware Pairwise Loss. It also evaluates on the public PHD dataset. Code: github.com/ICME24/KLive — [arXiv 2407.12002](https://arxiv.org/abs/2407.12002v1)
- HiVid (ICLR 2026, arXiv 2602.14214) uses an LLM to score chunk-level saliency for VOD and live streams, and predicts future weights from past ratings to meet latency limits. It reports up to 11.5% (VOD) and 26% (live) gains over baselines. Its focus is QoE/saliency, not clip extraction — [arXiv 2602.14214](https://arxiv.org/html/2602.14214v1)
- LiViBench (AAAI 2026) is a benchmark for interactive livestream video understanding across audio, speech and comments. It is not a highlight benchmark — [AAAI](https://ojs.aaai.org/index.php/AAAI/article/view/39859/43820)
- AntPivot (arXiv 2206.04888, 2022) frames livestream highlight detection as a task and uses hierarchical attention for very long streams with topic shifts — [arXiv 2206.04888](https://arxiv.org/abs/2206.04888v1)
- Fu et al., EMNLP 2017: a chat+video highlight dataset of 218 NALCS + 103 LMS League of Legends Twitch videos, labelled from community-made highlights — [ACL Anthology D17-1102](https://aclanthology.org/D17-1102/)
- LIGHTOR (ICDE 2020): implicit crowdsourcing from time-stamped chat, refined with viewer interaction. Dataset of 60 Dota 2 Twitch VODs — [arXiv 1910.12201](https://arxiv.org/pdf/1910.12201)
- MINT combines chat emotes and reactions, video metadata and view counts to find "epic moments". Code and a clip dataset are on GitHub — [BMC blog](https://blogs.biomedcentral.com/on-physicalsciences/2021/09/02/epic-moments-live-streaming/)
- Ringer PhD thesis (York, 2022) covers multimodal livestream highlight detection, including chat-based methods — [White Rose eTheses](https://etheses.whiterose.ac.uk/32406/)
- Bilibili danmaku: Ping & Chen 2017 released danmaku word embeddings (~2.1M comments), a 5-emotion danmaku lexicon, and highlight gold standards for 11 videos — [GitHub ChanningPing/VideoHighlightDetection](https://github.com/ChanningPing/VideoHighlightDetection); [arXiv 1708.02210](https://arxiv.org/pdf/1708.02210)
- DanmakuTPPBench (2025): 7,250 Bilibili videos and 10,820,790 danmaku events, aimed at temporal point process modelling and QA, not highlights — [arXiv 2505.18411](https://arxiv.org/html/2505.18411v1)
- The "COHETS" HF dataset card (65 Twitch videos, 9,128 min, with chat) is empty and reads like boilerplate. Treat it as unverified — [HF datasets/samjaylin/COHETS](https://huggingface.co/datasets/samjaylin/COHETS)

Weights are on Zenodo 3987831, and the full bundle is ~5.6 GB. - EfficientAT (MobileNetV3 distilled from PaSST): mn10_as has ~4.9M params and ~0.471–0.478 mAP, and the largest single model reaches ~0.483 mAP. License **MIT** per a downstream Core ML port that inherits from fschmid56/EfficientAT (not checked against the LICENSE file) — [GitHub fschmid56/EfficientAT](https://github.com/fschmid56/EfficientAT); [HF schism-audio Core ML port](https://huggingface.co/schism-audio/efficient-at-mn10-coreml); [arXiv 2211.04772](https://arxiv.org/html/2211.04772v3)
- BEATs (Microsoft): AS2M fine-tuned iter3+ checkpoints are linked as OneDrive downloads. The README says only "licensed under the license found in the LICENSE file in the root directory". A third-party re-host says the weights are MIT. Not verified — [GitHub microsoft/unilm/beats](https://github.com/microsoft/unilm/tree/master/beats); [HF Bencr/beats-checkpoints](https://huggingface.co/datasets/Bencr/beats-checkpoints/blob/main/README.md)
- LAION CLAP (clap-htsat-fused, larger_clap_general): the HF cards say **Apache-2.0**, but the fused card's citation block says CC BY 4.0 (conflict). It supports zero-shot audio classification against free-text labels via a transformers pipeline — [HF laion/clap-htsat-fused](https://huggingface.co/laion/clap-htsat-fused); [HF laion/larger_clap_general](https://huggingface.co/laion/larger_clap_general)
- SenseVoice-Small (FunAudioLLM): one model does ASR, language ID, speech emotion and audio events (music, applause, laughter, crying, coughing, sneezing) for zh/yue/en/**ja/ko**. License: **FunASR Model License v1.1** (custom, "not Apache-2.0 and not an OSI-approved open-source license"). ONNX and GGUF ports exist — [HF FunAudioLLM/SenseVoiceSmall](https://huggingface.co/FunAudioLLM/SenseVoiceSmall); [HF OpenVoiceOS ONNX port](https://huggingface.co/OpenVoiceOS/sensevoice-small-onnx)
- emotion2vec_plus_large (~300M params): speech emotion recognition. The official card says license "other" (FunASR MODEL_LICENSE). One GGUF port claims MIT, which conflicts — [HF emotion2vec_plus_large](https://huggingface.co/emotion2vec/emotion2vec_plus_large/blob/7714a5c669f5711ac128c78f35732e7f9cc976ad/README.md); [HF mlx-community port](https://huggingface.co/mlx-community/emotion2vec-plus-large-mlx)
- jrgillick/laughter-detection ("Robust Laughter Detection in Noisy Environments", Interspeech 2021): PyTorch, with a `segment_laughter.py` CLI and AudioSet-based laughter annotations. The upstream license was not confirmed. A fork is MIT — [GitHub jrgillick/laughter-detection](https://www.github.com/jrgillick/laughter-detection); [fork listing](https://awesome.ecosyste.ms/projects/github.com%2Fariym%2Flaughter-detection)
- IDEO LaughDetection releases pretrained models and rebalanced data under **CC BY 4.0** — [GitHub ideo/LaughDetection](https://github.com/ideo/LaughDetection)
- Qwen3-Omni-30B-A3B-Captioner (Apache 2.0) can caption ≤30 s audio clips (see above). It could describe *why* a candidate moment is loud, but only for short clips — [HF Captioner card](https://huggingface.co/Qwen/Qwen3-Omni-30B-A3B-Captioner)

### Inferences
- Recommended order for stream2clip: (1) add an AudioSet tagger as a new feature track next to RMS. EfficientAT mn10 (~4.9M params, MIT) is light enough to run over a multi-hour stream on CPU. PANNs CNN14 is heavier but has CC-BY-4.0 weights. Use the per-class probabilities for laughter, screaming, applause, cheering, music and singing as extra z-scored series in the same robust-z framework. This would replace the "loud, choppy" laughter heuristic and the singing heuristic with learned detectors. (2) Optionally re-rank the top N candidates with a local VLM (Qwen3-VL-4B/8B GGUF) on a few frames plus the transcript. Do not use it as a full-stream scanner, because small models' zero-shot temporal grounding is weak.
- KLive's design points map directly onto stream2clip's problem: chat lags the moment, so modalities need a cross-modal time-alignment step, and a causal look-back window is needed for live use. A simple version is to learn or estimate a chat-lag offset per stream by cross-correlating the chat rate with audio loudness or laughter probability.
- QVHighlights-style models (CoSTL, VideoLights, SG-DETR) solve text-query moment retrieval on short clips. They need CLIP/SlowFast features and their training data is not stream content, so they suit an optional "find the moment where X happens" search feature better than core scoring.
- There is no VTuber/Japanese live-stream highlight benchmark. stream2clip could build its own evaluation set from existing kirinuki: channels' clip timestamps on public VODs act like the community-highlight labels in Fu et al. 2017.
- License flags: SenseVoice and emotion2vec (custom FunASR license) should be optional user-installed plugins, not defaults. SenseVoice is attractive because one model gives ja/ko ASR plus laughter/applause/BGM event tags.

### Gaps
- I could not confirm the license text of BEATs checkpoints, EfficientAT's LICENSE file, or upstream jrgillick/laughter-detection. Only secondary or port statements were found.
- The AudioSet ontology page I fetched did not show the laughter/scream/applause subclasses or the label license. Class names should be checked against the 527-class label CSV shipped with PANNs or EfficientAT.
- No benchmark numbers were found for laughter detection on Japanese or Korean streams, or on VTuber audio (voice changers, game BGM).
- No 2025–2026 paper on chat-only highlight detection for Twitch or YouTube was found beyond the 2017–2022 work above. KLive's dataset release terms (Kuaishou) were not checked.
- No VRAM or speed figures were found for Qwen3-VL or Qwen3-Omni on consumer GPUs.

## 2. ASR for Japanese/Korean in 2026

### Takeaway
On clean Japanese (FLEURS), Whisper large-v3 is still the most accurate open model in a Sept 2026 comparison, with large-v3-turbo close behind at ~1.6x the speed. Parakeet-TDT-CTC-0.6B-ja (CC-BY-4.0) is about 10x faster still at ~1 point higher CER. Qwen3-ASR-1.7B (Apache-2.0, Jan 2026) is the strongest new candidate for noisy game audio, singing and Korean, and comes with a ja/ko forced aligner for word timestamps. All candidates except Qwen3-ASR's vLLM streaming path run offline on Windows.

### Cited Findings

**Head-to-head (Japanese, FLEURS test, 650 utterances, NVIDIA L40S, published 1 Sept 2026)**
- Normalized CER (NFKC, punctuation stripped) / raw CER / RTF / peak VRAM at the best batch size: Whisper large-v3 4.49% / 7.51% / 0.0077 / 20.1 GiB. **Whisper large-v3-turbo 4.81%** / 8.15% / 0.0048 / 11.1 GiB. **Parakeet TDT-CTC 0.6B ja 5.94%** / 9.41% / **0.0004** / 5.5 GiB. Kotoba-Whisper v2.2 6.92% / 12.27% / 0.0022 / 6.5 GiB. ReazonSpeech K2 v2 (sherpa-onnx CUDA) 9.40% / 15.01% / 0.0032 / 22.1 GiB. NVIDIA Nemotron 3.5 13.31%, but FLEURS is in its training data. The author's picks: large-v3 for accuracy, turbo for near-equal accuracy at ~1.6x throughput and half the VRAM, and Parakeet for bulk processing (2,482 audio-hours per hour). The author warns that FLEURS is clean read speech — [Classmethod DevelopersIO (ja)](https://dev.classmethod.jp/articles/japanese-asr-l40s-fleurs-benchmark/)
- A secondary note summarizing a Neosophie IT-domain benchmark says Qwen3-ASR-1.7B had the lowest Japanese CER of nine models, with Whisper large-v3-turbo next. kotoba-whisper scored poorly on IT terms and Parakeet was fastest. On proper-noun F1, Whisper was ahead of Qwen3-ASR (0.60 vs 0.58), and Parakeet and ReazonSpeech were much lower (0.15–0.25). This comes from a personal scrapbox page, not the primary report — [scrapbox tomiokario/ASR](https://scrapbox.io/tomiokario/ASR)

**Qwen3-ASR (Alibaba, released 29 Jan 2026)**
- Sizes: 0.6B and 1.7B, plus Qwen3-ForcedAligner-0.6B. License **Apache-2.0**. 30 languages including ja and ko, plus 22 Chinese dialects. Backends: a `qwen-asr` PyPI package with transformers or vLLM. Streaming works only via vLLM, with no batching or timestamps in that mode — [HF Qwen/Qwen3-ASR-1.7B](https://huggingface.co/Qwen/Qwen3-ASR-1.7B); [GitHub QwenLM/Qwen3-ASR](https://github.com/QwenLM/Qwen3-ASR); [PyPI qwen-asr](https://pypi.org/project/qwen-asr/)
- Tech report per-language error rates (1.7B / 0.6B): FLEURS **ja 5.20 / 8.33**, **ko 2.57 / 3.72**. CommonVoice ja 11.64 / 14.96, ko 5.88 / 8.48. MLC-SLM (conversational) ja 11.80 / 14.74, ko 8.61 / 10.31. The report gives no per-language Whisper-large-v3 ja/ko baselines — [Qwen3-ASR Technical Report, arXiv 2601.21337](https://arxiv.org/html/2601.21337)
- Robustness: on an internal ExtremeNoise set, Qwen3-ASR-1.7B scores 16.17 WER vs **63.17 for Whisper-large-v3**. On singing: M4Singer 5.98, EntireSongs-en with BGM 14.60, EntireSongs-zh with BGM 13.91. There are no ja/ko singing sets — [HF card](https://huggingface.co/Qwen/Qwen3-ASR-1.7B); [arXiv 2601.21337](https://arxiv.org/html/2601.21337)
- Speed (vLLM, ~2 min inputs): 1.7B RTF 0.0148 at concurrency 1, 0.6B RTF 0.0092 — [arXiv 2601.21337](https://arxiv.org/html/2601.21337)
- ForcedAligner-0.6B: word/sentence/paragraph timestamps for up to 5 min of speech in 11 languages including ja/ko. Average alignment shift is ja 42.4 ms and ko 37.2 ms on raw MFA-labelled audio (the HF card gives 42.2 ms for ja, a small discrepancy), rising to ja 81.3 ms when concatenated to 300 s — [arXiv 2601.21337](https://arxiv.org/html/2601.21337); [HF card](https://huggingface.co/Qwen/Qwen3-ASR-1.7B)

**Whisper large-v3-turbo caveats**
- Turbo cuts the decoder from 32 layers to 4. One write-up says Japanese stays at about large-v2 accuracy while Thai and Cantonese degrade — [ax Inc. on Medium](https://medium.com/axinc-ai/whisper-large-v3-turbo-high-accuracy-and-fast-speech-recognition-model-be2f6af77bdc)
- Users report large-v3 Japanese hallucinations clustering in silent or music-only sections — [openai/whisper discussion #1762](https://github.com/openai/whisper/discussions/1762). A single anecdote says turbo output Japanese song lyrics as English — [HF whisper-large-v3-turbo discussion #44](https://huggingface.co/openai/whisper-large-v3-turbo/discussions/44)
- A hallucination study (arXiv 2609.32560, unusual ID, unverified) reports similar median CER for turbo and large-v3 (0.087 vs 0.089) but a worse mean (0.348 vs 0.288) and more >2x-error outputs for turbo — [arXiv 2609.32560](https://arxiv.org/pdf/2609.32560)

**Runtime / timestamps / VAD**
- On an RTX 4070 with large-v3, faster-whisper runs at ~12x real-time vs ~8x for whisper.cpp CUDA (method not shown). Speed comparisons often time a single pre-loaded pass and mislead — [PromptQuorum](https://www.promptquorum.com/power-local-llm/local-whisper-stt-comparison); [TildAlice](https://dev.to/tildalice/whispercpp-vs-faster-whisper-why-speed-tests-lie-107o); [faster-whisper issue #1030](https://github.com/SYSTRAN/faster-whisper/issues/1030)
- faster-whisper supports `word_timestamps=True`. CTranslate2 timestamp computation differs from the transformers implementation, so accuracy should be tested — [faster-whisper issue #12](https://github.com/systran/faster-whisper/issues/12); [HF faster_CrisperWhisper](https://huggingface.co/nyrahealth/faster_CrisperWhisper)
- Silero VAD v5 (ONNX) is **MIT** (keep the copyright notice) and is the usual pre-filter against hallucinations in silent or BGM-only stretches — [Praat manual: Silero VAD MIT License](https://www.fon.hum.uva.nl/praat/manual/Silero_VAD_MIT_License.html); [HF onemira/silero-vad-onnx](https://huggingface.co/onemira/silero-vad-onnx)

### Inferences
- **Quick win:** make large-v3-turbo the default "quality" model in place of small/medium. It stays in the existing faster-whisper/CTranslate2 path, needs about half of large-v3's VRAM, and loses only ~0.3 CER points on clean Japanese. Pair it with Silero VAD gating to suppress BGM hallucinations.
- **Fast path:** Parakeet-TDT-CTC-0.6B-ja (CC-BY-4.0, attribution in the About box) for Japanese-only bulk or preview transcription. It needs NeMo, or a GGUF/ONNX/sherpa-onnx runtime to avoid a heavy PyTorch+NeMo install on Windows. It is Japanese-only, and the proper-noun weakness matters for VTuber names, so a user dictionary or post-correction is needed.
- **Robust path for game audio, singing and Korean:** Qwen3-ASR-1.7B via the transformers backend, plus Qwen3-ForcedAligner-0.6B for karaoke word timing. The ExtremeNoise and BGM-song results are the most relevant evidence for VTuber game streams and karaoke streams. vLLM is mainly a Linux runtime (my understanding, not checked), so Windows users would use the slower transformers backend. Its FLEURS-ko 2.57 is the best Korean figure found for an Apache model.
- The forced aligner could also re-time Whisper output, which addresses known faster-whisper word-timestamp drift in Japanese without changing the ASR model.
- kotoba-whisper v2.x now trails turbo on FLEURS in the 2026 test, so its main remaining advantage is speed on modest GPUs.

### Gaps
- No benchmark on VTuber or game-stream audio (BGM, SFX, voice effects, shouting) for any model. Every number above is on read or conversational speech.
- No VRAM numbers at batch size 1 on consumer GPUs (8–12 GB) for Qwen3-ASR or Parakeet. The L40S numbers are at batch 32–64.
- No CPU-only Windows benchmarks for large-v3-turbo, Parakeet-ja or Qwen3-ASR.
- No independent KsponSpeech comparison of Qwen3-ASR, turbo and Korean fine-tunes. The licenses of batisay and BuzzASR were not checked.
- No source found on Qwen3-ASR or the aligner working on native Windows without vLLM, or on whether ONNX/GGUF exports exist.

## 3. Speaker diarization

### Takeaway
pyannote `speaker-diarization-community-1` (pyannote.audio 4.x, CC-BY-4.0) is the best permissive built-in option. It is gated on Hugging Face, so the user must accept terms with their own token, or stream2clip has to ship clear first-run instructions. DiariZen is more accurate but its weights are **non-commercial (CC BY-NC 4.0)**. NVIDIA Streaming Sortformer v2 is CC-BY-4.0 but capped at 4 speakers. sherpa-onnx pipelines offer a lighter CPU/ONNX path.

### Cited Findings
- **pyannote community-1:** "released under the CC-BY-4.0 license and will always remain freely accessible". Gated: users must accept conditions, including agreeing to pyannote emails, and use an HF token. It runs on CPU by default and can be moved to CUDA. Offline use works by git-cloning the repo, which needs a write-permission token. It adds an `exclusive_speaker_diarization` output, backported from the commercial Precision-2, for easier alignment with ASR words. No RTF or speed figures are published — [HF pyannote/speaker-diarization-community-1](https://huggingface.co/pyannote/speaker-diarization-community-1); [pyannote blog: community-1](https://pyannote.ai/blog/community-1)
- DER (%), 3.1 → community-1 → Precision-2 (paid API): AMI-IHM 18.8 → 17.0 → 12.9. AliMeeting 24.5 → 20.3 → 15.2. DIHARD3 21.4 → 20.2 → 14.7. MSDWild 25.4 → 22.8 → 17.3. VoxConverse 11.2 → 11.2 → 8.5. AVA-AVD 49.7 → 44.6 → 37.1. Community-1 beats 3.1 on 10 of 12 sets. No Japanese benchmark is listed — [HF community-1 card](https://huggingface.co/pyannote/speaker-diarization-community-1)
- pyannote.audio (the library) is MIT — [Praat manual: pyannote.audio MIT License](https://www.fon.hum.uva.nl/praat/manual/pyannote_audio_MIT_License.html). Version 4.x is on PyPI — [PyPI pyannote-audio 4.0.1](https://pypi.org/project/pyannote-audio/4.0.1/). The older 3.1 pipeline is MIT but requires accepting the gated segmentation-3.0 conditions — [GitHub pyannote/hf-speaker-diarization-3.1](https://www.github.com/pyannote/hf-speaker-diarization-3.1)
- **DiariZen (BUT-FIT, WavLM-based):** code MIT, **weights CC BY-NC 4.0**, because some training data is research-only. A format conversion does not broaden this — [BUT-FIT card (mirror)](https://good23hfaccelerating.pages.dev/BUT-FIT/diarizen-wavlm-large-s80-mlc/blob/main/README.md); [HF OpenASR/diarizen-large-s80-v2](https://huggingface.co/OpenASR/diarizen-large-s80-v2). Tutorial paper (2026): [arXiv 2604.21507](https://arxiv.org/pdf/2604.21507). Structured-pruning work aims at efficiency — [arXiv 2506.18623](https://arxiv.org/pdf/2506.18623)
- SUPlime (WavLM, pyannote-compatible) is also CC BY-NC 4.0 — [HF rewayai/suplime](https://huggingface.co/rewayai/suplime)
- **NVIDIA Streaming Sortformer:** `diar_streaming_sortformer_4spk-v2` is **CC-BY-4.0**. The newer v2.1 is under the NVIDIA Open Model License ("other") and is the default in NeMo voice-agent docs. ONNX exports exist — [HF sortformer 4spk-v2](https://huggingface.co/nvidia/diar_streaming_sortformer_4spk-v2); [HF sortformer 4spk-v2.1](https://huggingface.co/nvidia/diar_streaming_sortformer_4spk-v2.1); [NeMo docs](https://docs.nvidia.com/nemo/labs-voice-agent/about/core-concepts/speech-pipeline/speaker-diarization); [HF ONNX export](https://huggingface.co/Recogment/sortformer-4spk-v2-onnx); [paper arXiv 2507.18446](https://arxiv.org/html/2507.18446v1)
- **sherpa-onnx diarization:** pyannote-3.0 segmentation (ONNX) + an embedding extractor (3D-Speaker, NeMo or WeSpeaker) + fast clustering. WeSpeaker embeddings are Apache-2.0 per a packaging source. A Rust port (pyannote-rs) also exists — [sherpa-onnx diarization models](https://csukuangfj.github.io/sherpa/onnx/speaker-diarization/models.html); [HF 42ailab packaging](https://huggingface.co/42ailab/Speaker-Diarization-Models); [docs.rs pyannote-rs](https://docs.rs/crate/pyannote-rs/0.3.4)
- kotoba-whisper-v2.2 bundles diarization and punctuation into a Japanese ASR pipeline — [HF kotoba-whisper-v2.2](https://huggingface.co/kotoba-tech/kotoba-whisper-v2.2)

### Inferences
- Built-in option: community-1 via pyannote.audio 4.x, behind an optional extra (`pip install stream2clip[diarize]`). The GUI should walk the user through accepting the HF gate. stream2clip must not redistribute the weights without the user accepting the gate, because the gate terms are attached to access even though the license is CC-BY-4.0. Keep RTTM, whisperX JSON and per-mic tracks as the zero-dependency paths.
- For collab streams with ≤4 speakers, Sortformer v2 (CC-BY-4.0) via ONNX is a gate-free alternative. Avoid v2.1 unless the NVIDIA Open Model License terms are acceptable.
- A CPU-only fallback is sherpa-onnx (segmentation + WeSpeaker embeddings), which avoids PyTorch entirely and suits the numpy/ffmpeg style of the project.
- DiariZen and SUPlime should only be documented as "bring your own model, non-commercial", since many clip channels are monetized.
- VTuber collabs have voice effects, overlapping laughter and BGM. Per-mic tracks stay the most reliable source when available. Diarization quality on such audio is unmeasured.

### Gaps
- No CPU real-time factors for community-1 on a multi-hour stream, and no DER results on Japanese or Korean speech.
- The 3D-Speaker embedding license and sherpa-onnx's own license were not confirmed in this pass.
- No public evaluation of diarization on VTuber collab audio with voice changers.

## 4. Local translation (ja→ko / ja→en, casual speech)

### Takeaway
The permissive (Apache-2.0) route is a general instruction LLM through llama.cpp/Ollama: Qwen3.5 (0.8B–9B) or Gemma 4 (E2B–31B). Translation-specialised models carry custom licenses (TranslateGemma: Gemma Terms of Use; PLaMo-2-translate: community license with a revenue cap; Hy-MT2: Tencent HY Community License excluding the EU). Hunyuan-MT-7B's license **excludes South Korea**. NLLB-200 is **non-commercial**. No public ja→ko casual-speech benchmark exists.

### Cited Findings
- **Qwen3.5 small models** (2 Mar 2026): dense 0.8B, 2B, 4B and 9B, **Apache-2.0**, native multilingual support including Japanese. No first-party GPTQ-Int4 quants (weights are BF16) — [HF Qwen/Qwen3.5-9B](https://huggingface.co/Qwen/Qwen3.5-9B); [Artificial Analysis (ja)](https://artificialanalysis.ai/ja/articles/qwen3-5-small-models); [Gigazine](https://gigazine.net/gsc_news/en/20260303-qwen-3-5-small)
- **Gemma 4** (2 Apr 2026): **Apache 2.0**. E2B (~2.3B effective), E4B, 26B MoE, 31B dense. 128K context on the edge models, 256K on the larger ones. Available on HF, Kaggle and Ollama — [The Next Web](https://thenextweb.com/news/google-gemma-4-open-models-apache-2-launch); [eWeek](https://www.eweek.com/news/google-gemma-4-apache-2-open-models/)
- **TranslateGemma** (Jan 2026; 4B/12B/27B; 55 languages including Japanese): license **Gemma Terms of Use** ("open weights", not OSI). Google claims no rights to outputs. The 4B scores MetricX 5.32 and COMET 81.6 on WMT24++. Input is limited to 2K tokens, and there is a fixed chat template with source/target language codes. GGUF quants run in llama.cpp, Ollama and LM Studio. Human evaluation found a ja→en decline traced to proper-name errors. Korean was not confirmed on the card I read — [Google blog](https://blog.google/innovation-and-ai/technology/developers-tools/translategemma/); [HF google/translategemma-4b-it](https://huggingface.co/google/translategemma-4b-it); [The Decoder](https://the-decoder.com/googles-new-open-translategemma-models-bring-translation-for-55-languages-to-laptops-and-phones/); [Gigazine](https://gigazine.net/gsc_news/en/20260116-google-translategemma); [arXiv 2601.09012](https://arxiv.org/abs/2601.09012v2)
- **Hunyuan-MT-7B:** Tencent Hunyuan Community License. The license "does not apply in the European Union, United Kingdom and South Korea", and use outside the territory is unlicensed — [Ollama-hosted license copy](https://ollama.com/SimonPu/Hunyuan-MT-Chimera-7B:Q8/blobs/4cd6b7965235); [Gigazine](https://gigazine.net/gsc_news/en/20250902-tencent-hunyuan-mt-7b)
- **Hy-MT2-7B** (open-sourced 21 May 2026): 33 languages, with ja and ko tags. License: **Tencent HY Community License**, whose text says it does not apply in the EU. A FlagOS mirror's Apache-2.0 claim conflicts with the official license. An unsloth GGUF exists — [HF tencent/Hy-MT2-7B](https://huggingface.co/tencent/Hy-MT2-7B); [Ollama license copy](https://ollama.com/kaelri/hy-mt2:7b/blobs/a0bce86d6ad2); [HF unsloth GGUF](https://huggingface.co/unsloth/Hy-MT2-7B-GGUF); [HF FlagOS mirror](https://huggingface.co/FlagRelease/HY-MT2-7B-hygon-FlagOS)
- **PLaMo-2-translate (PFN):** ja↔en only, PLaMo Community License. Free (including commercial use) for organizations and individuals under ¥1B annual revenue, and larger firms must buy a license. It is not chat-tuned. A vLLM recipe lists a ≥24 GB GPU. Ollama GGUF builds exist — [HF pfnet/plamo-2-translate](https://huggingface.co/pfnet/plamo-2-translate); [PFN press release](https://www.preferred.jp/en/news/pr20250527); [vLLM recipe](https://recipes.vllm.ai/pfnet/plamo-2-translate); [Ollama mitmul/plamo-2-translate](https://ollama.com/mitmul/plamo-2-translate:Q4_0-ssm-f16)
- **NLLB-200:** weights **CC-BY-NC 4.0** (non-commercial). Code (fairseq) is MIT. Wikimedia lists it as CC-BY-SA-NC, which conflicts — [HF nllb-200-distilled-600M](https://huggingface.co/facebook/nllb-200-distilled-600M/blob/main/README.md); [fairseq nllb README](https://github.com/facebookresearch/fairseq/blob/nllb/README.md); [Open-NLLB](https://github.com/gordicaleksa/Open-NLLB); [Wikimedia MT models table](https://meta.wikimedia.org/wiki/Machine_learning_models/Production/Machine_translation)
- **MADLAD-400:** Apache 2.0 for code and models according to Wikimedia's table (secondary, not checked at the source) — [Wikimedia MT models table](https://meta.wikimedia.org/wiki/Machine_learning_models/Production/Machine_translation)
- Benchmarks: JP-TL-Bench (Shisa.AI) covers ja↔en only, 70 items, including register and keigo — [arXiv 2601.00223](https://arxiv.org/html/2601.00223v1). A Korean multi-turn context translation benchmark has 216 Korean-source items × 3 targets — [kapitalismho benchmark README](https://raw.githubusercontent.com/kapitalismho/korean-llm-context-translation-benchmark/main/README.md). No dedicated ja→ko casual-conversation benchmark was found.

### Inferences
- Default built-in translator: a "local LLM translator" plugin that talks to any OpenAI-compatible endpoint (llama.cpp `llama-server`, Ollama, LM Studio), with Qwen3.5-4B/9B or Gemma 4 E4B as recommended models. Both are Apache-2.0. stream2clip can then document a model without bundling one, and the existing plugin boundary stays intact.
- For subtitle translation, pass a sliding window of previous and next lines plus a glossary (streamer name, fan name, recurring memes) in the prompt. TranslateGemma's proper-name errors and Parakeet/ReazonSpeech's weak proper-noun recall point to names as the main failure mode for VTuber content.
- Korea-based users should not be pointed at Hunyuan-MT-7B. Hy-MT2's territory clause should be read in full before recommending it. TranslateGemma is usable under Gemma ToU but should be labelled "custom license".
- ja→ko is a "close" language pair (shared word order and honorific systems). Casual-speech quality likely depends more on the LLM's colloquial Korean than on MT specialisation, but no benchmark confirms this. A small in-house eval set from translated kirinuki subtitles would be needed.

### Gaps
- No measured ja→ko quality for Qwen3.5, Gemma 4, TranslateGemma or Hy-MT2 on casual or streaming speech.
- TranslateGemma's language list was not confirmed to include Korean (55 languages claimed). The Gemma ToU clauses were not reviewed in detail.
- MADLAD-400's license was not confirmed on the Google or HF primary page. Sugoi Translator (Japanese-specialised) was not researched in this pass.
- No consumer-GPU tokens/sec or VRAM figures were collected for these models.

## 5. LLM use for titles/hooks/summaries/chapters and highlight ranking

### Takeaway
Open-source clippers in 2026 commonly use Whisper/faster-whisper, then an LLM (often a local Ollama model) to score transcript windows and output ranked clips, titles and chapters. No VTuber- or kirinuki-specific prompt pattern or evaluation was found. A local Apache-2.0 model (Qwen3.5, Gemma 4) through an OpenAI-compatible endpoint is the obvious integration, and instruction-tuned models are reported to be more stable for title generation.

### Cited Findings
- AutoClip (artbyjazi, **MIT**): runs fully offline with Whisper and Ollama, or with an API key. It outputs ranked, caption-burned, speaker-tracked 9:16 clips from a long video — [GitHub artbyjazi/autoclip](https://github.com/artbyjazi/autoclip)
- keydown-dev/clipper: FFmpeg + faster-whisper + any OpenAI-compatible endpoint (local Ollama works). The pipeline is transcribe → "score with a directive" → cut — [GitHub keydown-dev/clipper](https://github.com/keydown-dev/clipper)
- VideoHighlighter: offline Whisper subtitles plus Ollama-backed translation and chapter/story summarization — [GitHub Aseiel/VideoHighlighter](https://github.com/Aseiel/VideoHighlighter)
- AI-YouTube-Shorts-Generator: its "local mode" still needs a cloud LLM key — [GitHub](https://github.com/Anil-matcha/AI-Youtube-Shorts-Generator). FunClip (Alibaba) clips locally by transcript text or speaker using FunASR — [FunClip docs](https://docsearch.algolia.com/mcp/docs/repo/modelscope/funclip)
- A Feb 2025 Japanese study transcribed ~60-minute videos of a Japanese internet personality, grouped related segments, and used GPT-4o to drop off-topic sentences. Total length was cut to about a third — [Zenodo 14822841](https://zenodo.org/records/14822841)
- Hakuhodo Technologies (ANLP 2025) tested open-weight LLMs on ad-title generation. Instruction-tuned models were "significantly more stable" than non-tuned ones, and distilled Llama 3.2 was significantly worse than Llama 3.1 — [ANLP 2025 Q5-4](https://anlp.jp/proceedings/annual_meeting/2025/pdf_dir/Q5-4.pdf)
- HiVid (ICLR 2026) shows an LLM can rate chunk-level saliency for live streams under latency limits — [arXiv 2602.14214](https://arxiv.org/html/2602.14214v1)
- Local runtimes: llama.cpp is MIT — [Wikipedia](https://en.wikipedia.org/wiki/Llama.cpp). Qwen ships official GGUFs for VL models — [HF Qwen3-VL-8B-Thinking-GGUF](https://huggingface.co/Qwen/Qwen3-VL-8B-Thinking-GGUF). Qwen3.5 small models are Apache-2.0 — [HF Qwen3.5-9B](https://huggingface.co/Qwen/Qwen3.5-9B)

### Inferences
- The best fit for stream2clip's no-LLM-by-default design is an optional "LLM assist" plugin that receives structured data stream2clip already computes: candidate window transcript, chat-rate z-score, top chat phrases, laughter/scream probability and speaker labels. It returns JSON with a re-rank score, a one-line reason, 3 title candidates in the clip channel's style (【切り抜き】 prefix, name tags, and so on), and a chapter list. The scores stream2clip already computes stay the primary ranking. The LLM only breaks ties and writes text, which limits hallucinated moments.
- Few-shot prompting with the user's own past clip titles (a style memory) is likely to matter more than model size for kirinuki titles. This is untested.
- Chapters for full-stream archives can come from transcript segmentation (topic shifts) plus chat-rate peaks, with an LLM summarizing each segment. VideoHighlighter's chapter feature is a working local reference.

### Gaps
- No published prompt templates or evaluations for VTuber/kirinuki title generation, Japanese or Korean, local or cloud.
- No study comparing LLM re-ranking against chat/audio heuristics for stream highlights.
- Ollama's license and the context or VRAM needs for feeding a multi-hour transcript to a 4B–9B model were not researched.

## 6. Vision: anime/VTuber face and expression, scene change, OCR, thumbnail aesthetics, smart crop

### Takeaway
The current choice (deepghs YOLO ONNX anime face, MIT) remains appropriate. Permissive upgrades: TransNetV2 (MIT PyTorch port) or PySceneDetect (BSD-3) for cut detection, PaddleOCR PP-OCRv5 (Apache-2.0, Korean plus a Chinese model that covers Japanese) via RapidOCR/ONNX for game text, and the LAION CLIP+MLP aesthetic predictor (reportedly Apache-2.0) for thumbnail ranking. Watch-outs: deepghs anime_aesthetic is OpenRAIL, and aesthetic-predictor-v2.5 is reportedly AGPL-3.0.

### Cited Findings
- deepghs/anime_face_detection: **MIT** (card metadata), ONNX, v1 models ~3M params, with multiple versions (v1, v1.2, v1.3, s/n sizes). deepghs/imgutils-models is also MIT. The separate deepghs/yolo-face (real faces) has a "model-distribution-disclaimer-license" — [HF anime_face_detection README](https://huggingface.co/deepghs/anime_face_detection/blob/main/README.md); [HF imgutils-models](https://huggingface.co/deepghs/imgutils-models); [HF yolo-face](https://huggingface.co/deepghs/yolo-face)
- deepghs/anime_aesthetic is tagged **OpenRAIL** (use-restricted), and its training data is not documented. deepghs/ml-danbooru-onnx (tagger) is MIT — [HF anime_aesthetic README](https://huggingface.co/deepghs/anime_aesthetic/blob/main/README.md); [HF ml-danbooru-onnx](https://huggingface.co/deepghs/ml-danbooru-onnx)
- Aesthetic Predictor V2.5: SigLIP-based, scores 1–10 (≥5.5 is "great"), improved for illustrations. A third-party index lists the repo as **AGPL-3.0**, and the SigLIP encoder has its own license — [GitHub discus0434/aesthetic-predictor-v2-5](https://github.com/discus0434/aesthetic-predictor-v2-5); [ecosyste.ms listing](https://awesome.ecosyste.ms/projects/github.com%2Fdiscus0434%2Faesthetic-predictor-v2-5)
- LAION improved-aesthetic-predictor: an MLP on CLIP ViT-L/14 embeddings, ~20 MB head, used as a filter in NVIDIA NeMo Curator. Apache-2.0 per a Gitee mirror (unverified upstream) — [NeMo Curator docs](https://docs.nvidia.com/nemo/curator/curate-images/process-data/filters/aesthetic.md); [Gitee mirror](https://gitee.com/young_chiang/improved-aesthetic-predictor). A 2026 audit paper examines biases in the LAION-Aesthetics predictor — [arXiv 2601.09896](https://arxiv.org/pdf/2601.09896)
- TransNetV2: the `transnetv2-pytorch` PyPI package is **MIT**, inference-only, and "produces identical results as the original TensorFlow version". The upstream is soCzech/TransNetV2 — [PyPI transnetv2-pytorch](https://pypi.org/project/transnetv2-pytorch/); [HF magnusdtd/TransNetV2](https://huggingface.co/magnusdtd/TransNetV2/blob/main/README.md). AutoShot is a newer SBD dataset and method for short videos — [arXiv 2304.06116](https://arxiv.org/pdf/2304.06116)
- PySceneDetect: **BSD 3-Clause**. AdaptiveDetector is a two-pass detector that handles fast camera motion. 0.6.x is current on PyPI, and a 0.7 dev line (scenedetect-headless 0.7.1.dev0) exists — [PyPI scenedetect 0.6.2](https://pypi.org/project/scenedetect/0.6.2/); [PyPI scenedetect](https://pypi.python.org/pypi/scenedetect); [PyPI scenedetect-headless](https://pypi.org/project/scenedetect-headless/0.7.1.dev0/)
- PaddleOCR 3.x / PP-OCRv5: multilingual recognition in 37 languages including Korean (88.0% on its own set). Japanese is handled by the PP-OCRv5 Chinese model (Simplified, Traditional, Pinyin, English and Japanese in one model). Official ONNX recognizer exports exist and RapidOCR loads them. Apache-2.0 — [PP-OCRv5 multilingual docs](https://paddlepaddle.github.io/PaddleOCR/main/en/version3.x/algorithm/PP-OCRv5/PP-OCRv5_multi_languages.html); [HF PaddlePaddle/PP-OCRv5_server_rec_onnx](https://huggingface.co/PaddlePaddle/PP-OCRv5_server_rec_onnx); [HF monkt/paddleocr-onnx](https://huggingface.co/monkt/paddleocr-onnx/blob/main/README.md); [PaddleOCR 3.0 report arXiv 2507.05595](https://arxiv.org/abs/2507.05595)
- Qwen3-VL also does OCR in 32 languages (Apache-2.0) — [HF Qwen3-VL-4B-Instruct](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct)

### Inferences
- Thumbnails: replace pure Laplacian sharpness with a combined score: sharpness gate, plus anime face present and large (existing detector), plus eyes/mouth open if an expression model is found, plus the LAION CLIP+MLP aesthetic score. The LAION head is ~20 MB, but it needs a CLIP ViT-L/14 encoder (~400M params). An ONNX export would keep it torch-free. Avoid bundling AGPL (v2.5) or OpenRAIL (anime_aesthetic) models, and allow them only as user-installed plugins.
- Scene-change detection helps snap clip boundaries away from mid-cut and detects BRB or scene switches in OBS layouts. PySceneDetect's ContentDetector/AdaptiveDetector run on CPU and are pure-Python-friendly. TransNetV2 (PyTorch) is more accurate but adds a torch dependency.
- Game-text OCR (e.g. "GAME OVER", kill feed, result screens) via RapidOCR + PP-OCRv5 ONNX could become a highlight signal and could also supply proper nouns to correct ASR.
- Smart crop for vertical shorts: the existing avatar box from the anime face detector, smoothed over time (e.g. a Kalman or exponential filter on box centres), is likely enough. No VTuber-specific tracker was found.

### Gaps
- No anime or VTuber facial-expression classifier (smile, surprise, crying) with a clear permissive license was found in this pass.
- No research on Live2D/VTube Studio parameter capture (e.g. reading face-tracking data from VTube Studio's API) as an expression signal. This would be a non-ML alternative and was not checked.
- manga-ocr and other Japanese-specialised OCR were not checked. The LAION predictor's upstream license and the 3.x PaddleOCR weight license were confirmed only through mirrors.
- Saliency-based smart-crop models and their licenses were not researched.

## 7. Audio: music source separation (BGM removal), voice enhancement/denoise, loudness

### Takeaway
For removing BGM or copyrighted music, code is permissive everywhere (Demucs MIT, python-audio-separator MIT, ZFTurbo-style RoFormer inference MIT), but **weight licenses are unclear or restrictive**: HTDemucs weights' MIT tag is disputed (MUSDB training data), and community RoFormer vocal weights are variously labelled MIT or CC-BY-NC-SA-4.0. Demucs upstream is archived (Jan 2025). For denoise, DeepFilterNet3 (MIT/Apache-2.0, CPU real-time) and ClearerVoice MossFormer2_SE_48K (Apache-2.0) are clean choices.

### Cited Findings
- facebookresearch/demucs was archived on 1 Jan 2025. The maintainer left Meta and continues in the adefossez/demucs fork. Code is MIT — [GitHub facebookresearch/demucs](https://github.com/facebookresearch/demucs)
- The HTDemucs weights' MIT tag on HF is questioned in an open discussion, which suggests the weights may be "research purpose" because of MUSDB terms. No maintainer answer was found. Some re-hosts label the weights MIT, and another says no explicit weights grant was found — [HF adefossez/HTDemucs discussion #1](https://huggingface.co/adefossez/HTDemucs/discussions/1); [HF AEmotionStudio/htdemucs-models](https://huggingface.co/AEmotionStudio/htdemucs-models/blob/main/README.md)
- python-audio-separator (`audio-separator` on PyPI, MIT) runs UVR-family models (MDX-Net, VR, Demucs, BS/Mel-Band RoFormer), including "MelBand Roformer | Vocals by Kimberley Jensen", whose reported SDR varies by listing (~12.6 vs 10.98). Forks ask for credit to UVR for UVR-trained models — [PyPI audio-separator](https://pypi.org/project/audio-separator/); [GitHub python-audio-separator fork](https://github.com/melromyeah/python-audio-separator)
- RoFormer weight licenses conflict: one HF project says the BS/Mel-Band RoFormer weights are CC-BY-NC-SA-4.0 in their release metadata, while another card lists MIT for its conversions — [HF Ryan5453/unblend](https://huggingface.co/Ryan5453/unblend); [HF AEmotionStudio/roformer-models](https://huggingface.co/AEmotionStudio/roformer-models/blob/main/README.md)
- The MVSEP quality-checker leaderboard (undated snapshot) puts a BS-RoFormer entry from 2025.07.20 at ~14.58 vocals SDR and "BS PolarFormer Vocals (2026.05)" at ~14.03 — [MVSEP leaderboard](https://mvsep.com/quality_checker/leaderboard.php); [MVSEP entry 9933](https://mvsep.com/quality_checker/entry/9933)
- DeepFilterNet (v3, Interspeech 2023): framework and weights are open, code is dual Apache-2.0/MIT. RTF 0.19 on a single thread of an i5-8250U laptop CPU. DeepFilterNet2 targets full-band (48 kHz) real-time enhancement on embedded devices — [arXiv 2305.08227](https://arxiv.org/pdf/2305.08227); [GitHub mirror](https://github.com/lucribas/DeepFilterNet); [arXiv 2205.05474](https://arxiv.org/pdf/2205.05474)
- ClearerVoice-Studio (Alibaba): MossFormer2_SE_48K (48 kHz enhancement) and the SR_48K super-resolution card are **Apache-2.0**. The toolkit also has FRCRN_SE_16K and MossFormerGAN_SE_16K. Training used open and private data — [HF alibabasglab/MossFormer2_SE_48K](https://huggingface.co/alibabasglab/MossFormer2_SE_48K); [ClearerVoice-Studio paper arXiv 2506.19398](https://arxiv.org/html/2506.19398v1)

### Inferences
- BGM removal is legally and technically delicate. Separation lowers but does not eliminate Content ID matches, and the weights most likely to be best (MVSEP top entries) are mostly server-side or of unclear license. The safest product path is an optional "separate vocals" step via `audio-separator` with the user choosing and downloading the model, plus a UI note on the model's license. stream2clip should not bundle or auto-download any RoFormer or HTDemucs weights by default.
- A cheaper default that needs no separation model: reuse the AudioSet music/singing probabilities (Section 1) to detect copyrighted-music stretches and duck or skip them, or warn the user.
- DeepFilterNet3 is a good built-in "voice clarity" option for clips that keep game audio: CPU real-time, permissive, 48 kHz. ClearerVoice MossFormer2 is the heavier GPU option.
- Loudness: stream2clip already uses ffmpeg, whose two-pass `loudnorm` filter implements EBU R128 normalization to a platform target. This is from my own knowledge and was not verified in this pass.

### Gaps
- No primary statement of the license for the Kimberley Jensen Mel-Band RoFormer weights or the ZFTurbo checkpoints was found.
- No data on how well vocal separation defeats YouTube Content ID (an empirical and policy question, not covered).
- pyloudnorm, ffmpeg loudnorm docs and platform loudness targets were not fetched in this pass.
- No measurements of separation speed (CPU/GPU) for RoFormer models on consumer hardware.

## 8. Caption rendering: animated word-by-word styles in ASS/libass vs other renderers

### Takeaway
libass covers TikTok/Shorts-style captions well: `\kf` per-word fill, `\t()` per-word scale/colour pops, `\move`/`\fad`. PyonFX (Python) generates these programmatically from word timings. Browser-based renderers (pycaps, MIT, CSS-styled) offer richer effects at the cost of a headless-browser dependency. Remotion's license is not open source for organizations of 4+ people, so it does not fit an MIT tool.

### Cited Findings
- Word-level karaoke in ASS: each word becomes `{\kf52}word` (centiseconds), and libass fills each word left to right over its `\kf` duration. A reported pitfall: `\k` and `\t` times are relative to the line start while pipelines use absolute times — [DEV: captions that read along one word at a time](https://dev.to/danielrusnok/captions-that-read-along-one-word-at-a-time-3alg); [oxideav-ass animate.rs (timing semantics)](https://docs.rs/oxideav-ass/0.0.7/src/oxideav_ass/animate.rs.html)
- Aegisub Karaoke Templater's canonical per-syllable "pop": `{\r\k$kdur\t($start,$end,\1c&H00FF00&)\t($start,$mid,\fscy120)\t($mid,$end,\fscy100)}`. Colour change plus vertical scale bounce timed to each syllable — [Aegisub karaoke templater tutorial](https://aegisub.org/docs/3.5/automation/karaoke_templater/tutorial_1/); [Aegisub inline-fx](https://aegisub.org/docs/3.5/karaoke_inline-fx/)
- PyonFX is a Python 3 library for building ASS karaoke effects and typesetting with libass-supported tags. Its docs warn that very short syllables (fast singing) may make effects invisible — [GitHub CoffeeStraw/PyonFX](https://github.com/CoffeeStraw/PyonFX/); [PyonFX quick start](https://pyonfx.readthedocs.io/en/latest/quick%20start.html)
- pycaps (Franco Zanardi): MIT per a README mirror. It styles words with CSS, including a `.word-being-narrated` state for karaoke highlight, was tested on Python 3.10–3.12, and is "in active development" — [pycaps README mirror](https://gh.r-mj.com/yehigo/pycaps); [DEV tutorial](https://dev.to/francozanardi/adding-animated-subtitles-to-videos-with-python-4hml)
- Remotion is free for individuals and companies with ≤3 total headcount. Others need a Company License ($25/month per creator seat, or automation at $0.01 per render with a $100/month minimum). The license will change in Remotion 5.0. Its TikTok captions template follows the same terms — [Remotion LICENSE.md](https://unpkg.com/remotion@4.0.524/LICENSE.md); [Remotion license FAQ](https://www.remotion.dev/docs/license/faq); [remotion-dev/template-tiktok](https://github.com/remotion-dev/template-tiktok)
- Other caption renderers exist, such as PupCaps (a CLI for animated captions) — [GitHub hosuaby/PupCaps](https://github.com/hosuaby/PupCaps)

### Inferences
- Staying with ASS/libass is right for stream2clip: ffmpeg burns it in with no extra runtime, it works offline on Windows, and users can open it in Aegisub. Upgrades achievable within libass: (1) a per-word scale pop with `\t` (as in the templater snippet), (2) colour change of the active word only, by emitting one Dialogue line per active word or using `\kf` plus `\t` on `\1c`, (3) per-speaker colours, which already exist, (4) `\fad` entry and `\move` slide-ups for hook text. Using PyonFX as a generator would avoid hand-writing tag strings.
- Accurate word timestamps are what limit karaoke quality. The Qwen3-ForcedAligner ja/ko numbers (Section 2) are a direct upgrade path for `\kf` timing.
- Effects libass cannot do well include gradients per glyph, drop-in emoji/stickers synced to words, and mixed raster overlays. These need a compositor (pycaps-style browser rendering, or Pillow-rendered PNG overlays fed to ffmpeg `overlay`). The Pillow route fits the existing numpy/Pillow core and avoids a browser.

### Gaps
- pycaps' official repository license and its rendering backend (browser engine) were not confirmed from the primary repo.
- No benchmark of libass render speed for heavy per-word `\t` effects on long clips.
- No survey of which animated caption styles perform best on Shorts or kirinuki clips (an engagement question).
