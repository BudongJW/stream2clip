# stream2clip이 채울 버튜버 영상 도구의 빈칸

6개 분야를 조사한 결론은 이렇다. **범용 부품은 성숙했고 대부분 관대한 라이선스로 쓸 수 있지만, 이를 버튜버 방송에 맞게 묶은 도구는 사실상 없다.** yt-dlp, faster-whisper/WhisperX, libass, MediaPipe, three-vrm 같은 부품이 여기에 해당한다. 오픈소스 쇼츠 생성기는 2025~2026년에 수십 개로 늘었다. 대표적으로 zhouxiaoka/autoclip(약 10.7k★)과 Anil-matcha/AI-Youtube-Shorts-Generator(약 6.2k★)가 있다. 그런데 이들은 모두 실사 얼굴 추적을 전제로 한다. 웹캠과 게임 화면을 나누는 레이아웃을 가진 Clips Kitty조차 해당 모드를 "People on camera only, no VTubers"로 명시한다. 유일하게 찾은 VTuber 전용 SaaS인 VTubeClip은 조사일(2026-11-18)에 HTTP 410 Gone을 반환했다. 키리누키(切り抜き) 하이라이트 검출 기법은 "채팅 급증 + 반응 어휘 + 오디오" 융합이라는 공통 레시피로 모였다. 하지만 이를 구현한 저장소는 0~60★ 수준의 소규모뿐이다. 렌더링, Live2D, 3D 분야에는 "방송 중 아바타 파라미터를 녹화했다가 세로 화면으로 재렌더링하는 도구"도, "Live2D 모델 + 오디오 → 투명 배경 영상"을 만드는 단일 CLI도 없다. 엔드투엔드 파이프라인에 가장 가까운 레퍼런스는 빌리빌리 생태계의 biliup(MIT)과 bilive(Apache-2.0)다. 반면 라이선스 함정은 곳곳에 있다. AGPL 클리퍼(Clips Kitty, hotclip)와 비상업 라이선스로 바뀐 supoclip, ultralytics YOLO가 있고, Live2D Cubism Core는 독점 라이선스이며 "Expandable Application" 조항까지 붙는다. Hunyuan3D 2.0은 한국을 적용 범위에서 제외하고, THA4와 GVHMR은 비상업 전용이다. 따라서 stream2clip은 MIT/Apache 부품으로 본체를 꾸리고, 다음 네 가지를 차별점으로 삼는 것이 타당하다. 아바타 인식 레이아웃, CHZZK/SOOP 지원, 기획사 가이드라인 자동 준수, JP→KR 용어집 기반 자막이다.

> 이 보고서는 레퍼런스 모음의 요약본이다. 분야별 전체 목록, 세부 수치, 근거 URL은 `research_notes/버튜버 영상 작업 프로젝트 레퍼런스/`의 `01_shorts.md`(쇼츠), `02_kirinuki.md`(키리누키), `03_rendering.md`(렌더링), `04_live2d.md`(Live2D), `05_3d.md`(3D), `06_others.md`(기타)에 있다. CHZZK·SOOP 외부 오픈소스와 두 플랫폼의 공식 Open API는 2026-11-20 추가 조사인 `07_chzzk_soop.md`에 따로 정리했다. 표의 ★ 수는 2026-11-18 기준 근사치다. 상태 표기는 다음과 같다. "활발"은 최근 3개월 안에 push가 있는 경우, "정체"는 12~18개월 넘게 push가 없는 경우다. ⚠는 라이선스 위험, ☠는 서비스 종료·아카이브·폐기를 뜻한다.

## 1. 쇼츠 제작: 오픈소스 클리퍼 수십 개 중 버튜버를 인식하는 것은 없다

2026년 오픈소스 "OpusClip 대안"들은 거의 같은 레시피를 쓴다. yt-dlp로 받고, Whisper 계열 ASR로 단어 타임스탬프를 뽑고, LLM이 하이라이트에 점수를 매긴다. 이어서 MediaPipe나 YOLO로 얼굴을 추적해 9:16으로 크롭하고, ASS/libass 카라오케 자막을 ffmpeg로 입힌 뒤 선택적으로 업로드한다([zhouxiaoka/autoclip](https://github.com/zhouxiaoka/autoclip), [opensource-clipping](https://github.com/NaufalRizqullah/opensource-clipping)). 문제는 이 레시피가 **실사 얼굴(MediaPipe BlazeFace, YOLOv8-face, TalkNet)만 전제한다**는 점이다. 애니메이션 아바타 얼굴 추적을 문서화한 주류 OSS 클리퍼는 없었다.

VTuber 전용 저장소는 모두 초기 단계다. [billietomato/ytclip](https://github.com/billietomato/ytclip)(MIT, 3★)은 클립 제작과 번역 자막을 위한 Claude Code Agent Skills이고, [anAtheist987/AutoSlicer-v2](https://github.com/anAtheist987/AutoSlicer-v2)(MIT)는 歌枠(노래 방송)의 노래 구간을 검출한다. Clips Kitty의 웹캠/게임 분할 문제는 탐지기만 애니메 얼굴 검출기나 고정 영역으로 바꾸면 VTuber의 "아바타 + 게임" 레이아웃 문제와 같아진다. 애니메 얼굴 검출 부품은 이미 있다. [deepghs/anime_face_detection](https://huggingface.co/deepghs/anime_face_detection)(MIT, ONNX, F1 약 0.93~0.97)과 [hysts/anime-face-detector](https://github.com/hysts/anime-face-detector)(MIT, 28점 랜드마크)가 MIT이고, [Fuyucch1/yolov8_animeface](https://github.com/Fuyucch1/yolov8_animeface)는 ⚠ AGPL-3.0, [nagadomi/lbpcascade_animeface](https://github.com/nagadomi/lbpcascade_animeface)는 2018년 이후 정체이며 라이선스 파일이 없다.

상용 쪽 지형도 비슷하다. [OpusClip](https://www.opus.pro/), Vizard, Klap, Submagic 같은 범용 도구는 토킹헤드와 팟캐스트에 맞춰져 있다. 스트리머 특화 도구인 [StreamLadder](https://streamladder.com/)와 [Eklipse](https://eklipse.gg/features)는 VOD 가져오기, 페이스캠+게임 적층 레이아웃, 채팅 급증, 자동 게시를 제공하지만, 역시 실사 페이스캠과 게임 이벤트를 기준으로 튜닝돼 있다. **VTubeClip**은 아바타+게임 2단 세로 클립을 월 $3~16에 팔던 서비스다([AlternativeTo](https://alternativeto.net/software/vtubeclip/about/)). 2026-11-18에 사이트가 410을 반환해 ☠ 종료된 것으로 보인다. 프리랜서 VTuber 클리퍼가 클라이언트에게 **아바타 그린스크린 영상**을 따로 요구하는 관행([necroch.carrd.co](https://necroch.carrd.co/))도 있다. 이는 stream2clip이 합성된 방송 화면 외에 별도 아바타 소스를 입력으로 받아야 한다는 근거다.

부품 층위의 사실상 표준은 다음과 같다. 자막은 [pysubs2](https://github.com/tkarabela/pysubs2)로 ASS를 작성하고 [libass](https://github.com/libass/libass)를 쓰는 ffmpeg로 입힌다(macOS/Windows 기본 ffmpeg 빌드에는 libass가 빠져 있을 수 있다). CSS 애니메이션 자막이 필요하면 [pycaps](https://github.com/francozanardi/pycaps)(MIT, 알파)를 쓴다. [Remotion](https://github.com/remotion-dev/remotion)은 ⚠ 회사 규모에 따라 유료가 되는 커스텀 라이선스다. 리프레이밍에는 MediaPipe(Apache-2.0)가 기본이고, ⚠ [ultralytics](https://github.com/ultralytics/ultralytics)는 AGPL-3.0이라 YOLO를 번들하면 영향을 받는다. Google AutoFlip은 Bazel 빌드와 OpenCV 3에 묶인 레거시다. 업로드 쪽에서는 YouTube Data API `videos.insert` 공식 페이지가 **"Video Uploads 버킷 1 unit, 하루 100회, 미인증 프로젝트도 private 강제 아님"**이라고 적고 있다([Google](https://developers.google.com/youtube/v3/docs/videos/insert)). 아직도 널리 인용되는 "업로드 1회당 1,600 unit, 하루 약 6회" 규칙과 충돌하므로, 값을 하드코딩하지 말고 공식 페이지나 Cloud Console에서 확인해야 한다. CLI 레퍼런스로는 [porjo/youtubeuploader](https://github.com/porjo/youtubeuploader)(Apache-2.0, 활발)가 쓸 만하고, tokland/youtube-upload는 ☠ 2024년 이후 정체다. 방송 단계에서 세로 화면을 따로 확보하는 방법으로는 [Aitum/obs-vertical-canvas](https://github.com/Aitum/obs-vertical-canvas)(GPL-2.0)가 있다.

## 2. 키리누키: 검출 레시피는 굳어졌고, 쓸 만한 것은 코드가 아니라 파라미터다

"키리누키 엔진"이라 부를 만한 지배적 오픈소스는 없다. 소규모 저장소들이 같은 결론에 도달했을 뿐이다. 채팅을 10~30초 구간으로 묶고, 각 구간을 그 방송 자체의 기준선과 비교하고, 반응 어휘(草/w/lol/KEKW/ㅋㅋ)를 더한 뒤, 필요하면 오디오 음량이나 웃음 신호를 융합하고, 앞뒤 여유를 붙여 구간을 병합한다. 2025~2026년 신작은 여기에 Whisper 전사 위의 LLM 판정을 얹는다. 덧붙여 GitHub에서 "切り抜き"로 검색하면 대부분 이미지 배경 제거 도구가 나오므로 키워드 검색 결과만 보면 판단을 그르친다. 설계 레퍼런스로는 **파라미터를 문서로 공개한 저장소**가 가장 값지다.

수집 계층은 성숙해 있다. [yt-dlp](https://github.com/yt-dlp/yt-dlp)(Unlicense)는 `--download-sections`로 시간 구간만 받을 수 있고, `live_chat` 자막 트랙으로 라이브 채팅을, info dict의 `heatmap` 필드로 YouTube "가장 많이 다시 본 구간" 곡선(0~1)을 제공한다([common.py](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/common.py)). 덕분에 "1차로 채팅·heatmap만 받고 2차로 후보 구간만 다운로드"하는 저대역 설계가 가능하다. 채팅은 [xenova/chat-downloader](https://github.com/xenova/chat-downloader)(MIT, YouTube·Twitch, 유료 메시지 유형 필터 지원)가 받는다. 다만 마지막 push가 2025-11이라 고장 여부를 지켜봐야 한다. Twitch는 [lay295/TwitchDownloader](https://github.com/lay295/TwitchDownloader)(MIT, 채팅 JSON 다운로드와 렌더) 몫이다. 라이브 아카이빙은 [Kethsar/ytarchive](https://github.com/Kethsar/ytarchive)(MIT)가 맡는데, README가 `--potoken`을 사실상 필수라고 경고한다. 그 관리 도구인 [HoloArchivists/hoshinova](https://github.com/HoloArchivists/hoshinova)는 2024-04 이후 정체다. ☠ **[taizan-hokuto/pytchat](https://github.com/taizan-hokuto/pytchat)는 ARCHIVED(2021)이므로 의존하면 안 되고**, Python Twitch-Chat-Downloader(tcd)도 2022년 이후 정체다. 한국 플랫폼은 커뮤니티 소규모 도구뿐이다. [honey720/chzzk-vod-downloader-v2](https://github.com/honey720/chzzk-vod-downloader-v2)(⚠ GPL-3.0, 구간 다운로드), [321098123/chzzk-VOD-chat-downloader](https://github.com/321098123/chzzk-VOD-chat-downloader)(4★), [gunyu1019/chzzkpy](https://github.com/gunyu1019/chzzkpy)(MIT, 활발)가 있고, streamlink 본가에 `chzzk.py`·`soop.py` 플러그인이 있다([streamlink plugins](https://github.com/streamlink/streamlink/tree/master/src/streamlink/plugins)). YouTube, Twitch, CHZZK 채팅을 하나로 다루는 라이브러리는 없으므로 stream2clip은 내부 정규화 채팅 스키마와 플랫폼별 어댑터를 직접 정의해야 한다.

VTuber 고유 데이터 소스로는 **[Holodex API v2](https://docs.holodex.net/)**가 독보적이다. `include=clips,sources,refers`로 클립과 원본 방송의 연결 관계를, `GET /videos/{id}?c=1`로 타임스탬프 댓글을, `songs` include로 곡 구간을 받을 수 있다. 이 데이터는 "사람 클리퍼가 어느 장면을 잘랐는가"를 알려 주는 무료 약한 라벨(weak label)이 된다. 단, `X-APIKEY`가 필요하고 레이트리밋 수치는 공개되지 않았으며, ⚠ 약관이 API나 파생 콘텐츠에 프리미엄 과금을 금지하므로 상업화 전에 검토가 필요하다. 채팅 통계로는 [sigvt/vtuber-livechat-dataset](https://github.com/sigvt/vtuber-livechat-dataset)(VTuber 1B, 데이터 ODC-PDDL)가 있지만 2022년에서 멈췄다. 학술적으로는 [Fu et al. EMNLP 2017](https://aclanthology.org/D17-1102/), [LIGHTOR](https://arxiv.org/abs/1910.12201)(채팅으로 대략 위치를 잡고 시청 행동으로 정교화), MINT, 그리고 YouTube "Most replayed"를 라벨로 쓴 [Mr. HiSum(NeurIPS 2023)](https://proceedings.neurips.cc/paper_files/paper/2023/hash/7f880e3a325b06e3601af1384a653038-Abstract.html)이 "채팅+영상이 단일 신호보다 낫다"는 점을 일관되게 보인다. 다만 **VTuber나 키리누키를 직접 다룬 동료심사 논문은 IEICE FIT2023 F-014 초록 외에는 찾지 못했다**. 이 초록은 草/w 집계 방식이 채팅이 꺼진 방송에서 실패한다고 지적한다([IEICE](https://www.ieice.org/publications/conference-FIT-DVDs/FIT2023/data/html/program/pdf/F-014.pdf)). 상용·준상용 쪽에는 일본 시장의 [Highlight Analyzer](https://chromewebstore.google.com/detail/highlight-analyzeryoutube/pcicbonbpknjgpmofodbaiiljfhdbpok)(웃음 밀도·댓글 속도 그래프, 웃음 분석은 EN/JA/KO/ZH/ID 지원), 2020년의 Highlight-Ranking([INTERNET Watch](https://internet.watch.impress.co.jp/docs/yajiuma/1228457.html)), [KIRARI](https://www.producthunt.com/p/kirari/kirari)가 있다.

노트들에서 공통으로 읽히는 설계 교훈은 세 가지다. 첫째, 채팅은 사건 **뒤에** 반응하므로 피크에 −10~−30초 오프셋을 주어야 한다(HoloAutoClip 30초, ClipRadar −30/+60초). 둘째, 원시 메시지 수는 시청자 규모에 휘둘리므로 방송별 정규화, unique chatters 또는 엔트로피, 반복 문자 접기를 적용하는 편이 싸고 효과가 크다. 셋째, **슈퍼챗과 멤버십 급증을 명시적 신호로 쓰는 오픈소스는 하나도 없었다.** chat-downloader가 유료 메시지 유형을 노출하므로 데이터는 이미 손에 넣을 수 있다.

## 3. 버튜버 렌더링: 가장 싼 "재렌더링"은 방송 중 알파 레이어를 따로 녹화하는 것

Windows의 VTuber 앱은 사실상 모두 **Spout2로 알파(투명) 출력**을 지원한다. VTube Studio, Warudo, VSeeFace, VNyan, Animaze, PrprLive, EasyVtuber가 여기에 해당한다. 크로스플랫폼 대안은 NDI다. 반면 가상 웹캠은 대개 알파를 잃는다. VTube Studio 위키는 아예 "You should never use green-screen"이라고 적고 있다([VTS wiki](https://github.com/DenchiSoft/VTubeStudio/wiki/Recording-Streaming-with-OBS)). 문제는 주요 앱 대부분이 클로즈드 소스라는 점이다. 그래서 다른 카메라 앵글이나 화면비로 다시 그리려면 **픽셀이 아니라 데이터**(motion3.json, WANIM/BVH/FBX, VMC 패킷)를 녹화해 stream2clip이 통제하는 엔진에서 렌더링해야 한다.

VMC 프로토콜(OSC/UDP, MIT 스펙)은 프레임마다 휴머노이드 본 전체, 블렌드셰이프, 루트, 카메라를 담는다([VMC spec](https://protocol.vmc.info/english.html)). 따라서 타임스탬프를 붙인 VMC 패킷 덤프는 엔진에 독립적인 완전한 녹화본이 된다. 다만 "녹화된 VMC 세션"의 표준 파일 형식은 없다. 도구마다 JSON 덤프, BVH, WANIM을 제각각 쓴다.

VTuber 방송에는 아바타를 구동할 실사 얼굴 영상이 없으므로 쓸 수 있는 것은 오디오 구동 계열(PersonaLive, EchoMimic v3, InfiniteTalk, MuseTalk)뿐이고, 결과는 스트리머의 실제 리그와 다르게 보인다. **클립 도구에서는 실제 모델을 충실하게 재렌더링하는 편이 AI 재애니메이션보다 낫고, AI는 모델 파일이나 파라미터가 없을 때의 대체 수단이다.** 이미지에서 아바타를 만드는 연구로는 [CharacterGen](https://github.com/zjp-shadow/CharacterGen)과 [StdGEN](https://github.com/hyz317/StdGEN)(Apache-2.0)이 있다. CartoonAlive([arXiv 2507.17327](https://arxiv.org/abs/2507.17327))와 Bunraku는 코드 공개 여부를 **확인하지 못했다**.

## 4. Live2D: 렌더러는 Pixi v8 포크로 해결되지만 관문은 Cubism Core 약관이다

공식 Live2D 생태계의 현재 상태는 다음과 같다. 안정 버전 Editor는 Cubism 5.3(2026-01-20)이고, 블렌드 모드와 오프스크린 드로잉이 추가됐다. 5.4는 2026-07-14부터 알파 단계이며, 무료판 기능은 5.3에서 끊긴다([Live2D 5.4 알파 공지](https://www.live2d.com/en/information/cubism-5_4-alpha/)). Framework 계층은 GitHub에 공개돼 있지만 런타임인 **Cubism Core는 Live2D Proprietary Software License**로 별도 배포된다([Cubism Core docs](https://docs.live2d.com/en/cubism-sdk-manual/cubism-core/)). ⚠ 라이선스 구조가 stream2clip에 직접 영향을 준다. 연매출 1,000만 엔 미만의 개인·소규모 사업자는 출시 라이선스가 면제된다. 그러나 **"Expandable Application"은 예외로 항상 심사와 특별 계약이 필요하고, Live2D는 "VTuber tracking software"를 그 예로 든다**([Live2D SDK license](https://www.live2d.com/en/sdk/license/)). 사용자가 자기 모델을 불러와 렌더링하는 도구가 이 범주에 들어가는지는 1차 원문으로 확정하지 못했다. 공개 배포 전에 Live2D에 직접 확인해야 한다. 연매출 2,000만 엔을 넘는 VTuber 사업자에게는 별도의 VTuber 라이선스 조건도 있다.

오프라인 클립 렌더링에 대해 노트가 내린 권장안은 명확하다. 실시간 `speak()`(Web Audio 재생)는 벽시계 시간에 묶이므로 쓰지 않는다. 대신 오디오에서 프레임 단위 입 파라미터를 미리 계산한다. RMS를 `ParamMouthOpenY`로 매핑하는 방식이 단순하고 견고하며, MFCC 모음 가중치를 `ParamA/I/U/E/O`로 보내면 더 자연스럽다. 그다음 고정 delta-time으로 모델을 갱신하며 RGBA 프레임을 캡처하고, ProRes 4444(`yuva444p10le`)나 VP9 알파 WebM으로 인코딩한다([Remotion transparent videos](https://www.remotion.dev/docs/transparent-videos)). Cubism Editor 내보내기는 straight alpha 방식이라 H.264에서 반투명 부분이 깨진다는 보고가 있다([Live2D docs](https://docs.live2d.com/en/cubism-editor-manual/exporting-images)). 5.3의 WebM 출력에 알파가 들어가는지는 **확인하지 못했다**. 결정적으로 **"Live2D 모델 + 오디오 파일 → 투명 영상"을 한 번에 해 주는 오픈소스 CLI는 존재하지 않았다.**

Live2D 공식 샘플은 Free Material License에 따라 연매출 1,000만 엔 미만 사용자에게만 상업 이용을 허용한다([Live2D Help](https://help.live2d.com/en/?p=2546)). nizima LIVE 샘플은 수정·재배포를 금지하고([nizima LIVE Sample Model Terms](https://docs.nizimalive.com/en/manual/samplemodel-terms/)), BOOTH 판매 모델은 상품별 약관을 따른다. ⚠ [Eikanya/Live2d-model](https://github.com/Eikanya/Live2d-model)(3.5k★) 같은 "모델 모음" 저장소는 라이선스가 없고 게임에서 추출한 자산을 담은 경우가 많다. 따라서 stream2clip 저장소에는 샘플 모델을 커밋하지 말고, 사용자가 약관에 동의한 뒤 설치 시점에 내려받게 해야 한다. 2026년에 새로 나온 오픈 퍼펫 엔진인 [AyagamiDev/ayagami](https://github.com/AyagamiDev/ayagami)(Apache-2.0), [zeikar/iki](https://github.com/zeikar/iki)(MIT), [livliv-dev/player](https://github.com/livliv-dev/player)(Apache-2.0, 생성 2주차에 1.6k★)는 아직 수주~수개월 된 프로젝트라 관찰 목록에 둔다.

## 5. 3D: VRM 1.0 메타 덕분에 아바타 권리 검사를 자동화할 수 있다

3D 쪽은 2D보다 표준화가 잘 돼 있다. VRM 1.0(glTF 기반)과 VRMA(`.vrma`, VRM Animation)는 모두 정식 스펙이다. Unity, three.js, Blender, Godot, Unreal의 주요 구현 다섯 가지가 모두 MIT이고 2026년에도 유지보수된다. stream2clip에 특히 중요한 것은 **VRM 1.0 meta에 기계가 읽을 수 있는 사용 허가 필드가 있다는 점**이다. `avatarPermission`, `commercialUsage`(`personalNonProfit`/`personalProfit`/`corporation`), `creditNotation`, `modification`, `allowRedistribution`, 그리고 폭력·성적·정치 표현 허용 여부가 여기에 들어간다([meta.md](https://raw.githubusercontent.com/vrm-c/vrm-specification/master/specification/VRMC_vrm-1.0/meta.md)). 이 필드를 읽으면 렌더링 전에 "비영리 전용 모델을 수익화 채널에서 쓰는지", "크레딧 표기가 필요한지"를 자동으로 검사할 수 있다. VRM 0.x 메타 필드는 원문으로 확인하지 못했지만, 0.x 모델이 아직 많으므로 두 버전 모두 파싱해야 한다.

"VRM + 모션 → MP4"를 한 번에 해 주는 기성 오픈소스는 찾지 못했다. 대신 three-vrm + VRMA 씬을 결정론적으로 seek하고, Remotion `@remotion/three`, Puppeteer, @headless-three/renderer 중 하나로 프레임을 캡처한 뒤 ffmpeg로 방송 원본과 합성하면 된다. 단 Remotion은 ⚠ 일정 규모 이상의 영리 조직에 Company License를 요구한다([Remotion LICENSE](https://cdn.jsdelivr.net/gh/remotion-dev/remotion@main/LICENSE.md)). MMD 쪽에서는 three.js 공식 MMDLoader가 r172 이후 제거돼 [@yohawing/three-mmd-loader](https://registry.npmjs.org/@yohawing/three-mmd-loader)와 [babylon-mmd](https://github.com/noname0310/babylon-mmd)(둘 다 MIT)로 옮겨 갔다. **VMD를 VRMA로 바로 변환하는 공개 도구는 없었다.** 3D에서 장기적으로 가장 값진 기능은 영상에서 포즈를 추정하는 것이 아니다. 방송 중에 흐르는 VMC 패킷을 녹화해 VRMA로 변환하는 것이다. 이 경로가 실사 인체용 모델(4D-Humans 등)로 애니메 체형을 추정하는 것보다 정확하고, 라이선스도 깨끗하다.

## 6. 기타: 엔드투엔드에 가장 가까운 레퍼런스는 빌리빌리 생태계에 있다

"녹화 → 하이라이트 → 편집 → 자막 → 업로드" 전 과정을 오픈소스로 묶은 사례는 중국 빌리빌리 생태계에만 있었다. [biliup/biliup](https://github.com/biliup/biliup)(MIT, ~5.6k★, 활발)은 19개 플랫폼(YouTube, Twitch, TwitCasting, niconico, AfreecaTV 포함)을 24시간 녹화하며 탄막을 동기 저장한다. [timerring/bilive](https://github.com/timerring/bilive)(Apache-2.0, ~3.3k★, 둔화)는 탄막 밀도로 자르고 멀티모달 LLM으로 제목과 커버를 만든 뒤 자동 업로드한다. **일본어·한국어권에서는 이 수준으로 통합된 오픈소스를 찾지 못했고**, CHZZK 쪽은 [d2n0s4ur/chzzk-downloader](https://github.com/d2n0s4ur/chzzk-downloader) 같은 녹화 스크립트 수준에 머문다.

이 분야에서 stream2clip에 바로 쓸 만한 설계는 두 가지다. 하나는 크리에이터 본인용 "라이브 모드"다. obs-websocket에 연결해 두고 채팅 급증이나 Streamer.bot 이벤트가 오면 `SaveReplayBuffer`를 호출하고, `ReplayBufferSaved`로 받은 파일 경로를 후처리 큐에 넣는다. 다른 하나는 음악 처리다. 노래 구간을 탐지해(inaSpeechSegmenter) 후보에서 제외하거나 경고하고, 필요하면 BGM을 감쇠한다. 노래 방송(歌枠)은 곡 저작권 때문에 위험도가 높으므로, Holodex·Musicdex의 곡 구간 데이터는 오히려 **제외 구간**을 정하는 데 쓰는 편이 맞다. 통계 사이트([Playboard](https://playboard.co/en/youtube-ranking/most-superchatted-v-tuber-channels-in-worldwide-weekly), [StreamsCharts](https://streamscharts.com/api))는 채널 우선순위를 정하는 참고 자료일 뿐이다. 유료이거나 정확도 논란이 있어 파이프라인 입력으로는 맞지 않는다. 마지막으로 **VTuber 본인 목소리를 RVC 등으로 클론해 내레이션에 쓰는 기능은 넣지 말아야 한다.** hololive 음악 가이드라인이 탤런트 음성으로 음성을 생성하는 것을 거부하기 때문이다([hololive terms](https://hololivepro.com/terms/)).

## 조사로 드러난 빈칸: 아바타 인식, 재렌더, 한국 플랫폼, 컴플라이언스

가장 큰 빈칸은 **VTuber를 인식하는 쇼츠 도구**다. 실사 얼굴 추적을 전제로 한 OSS 클리퍼는 넘쳐나지만, 애니메 아바타 박스를 자동으로 제안하고 "아바타 + 게임" 세로 레이아웃을 만드는 도구는 없다. 가장 가까운 OSS(Clips Kitty)는 VTuber를 명시적으로 빼놓았고, 유일한 SaaS(VTubeClip)는 문을 닫은 것으로 보인다. 이 사실은 미충족 수요를 뜻할 수도 있고, 시장이 작다는 신호일 수도 있다. 둘 다 열어 두는 것이 정직한 해석이다. 두 번째는 **렌더링 계층의 빈칸 두 개**다. 하나는 Live2D 모델과 오디오 파일로 투명 영상을 만드는 단일 CLI가 없다는 것이고, 다른 하나는 방송 중 VMC/VTS 파라미터를 녹화했다가 새 화면비나 카메라 앵글로 재렌더하는 파이프라인이 없다는 것이다. 녹화 쪽 부품(MotionReplay, VRMPlaybackClient, vmc2bvh)은 모두 Windows/Unity 기반이고 정체됐다. VMD→VRMA 변환기도 공백이어서 stream2clip의 부산물 오픈소스가 될 수 있다.

세 번째는 **한국 플랫폼**이다. CHZZK/SOOP에는 다운로더, 채팅 수집기, 수동 편집점 타이머, ClipRadar 같은 소규모 도구만 있다. "CHZZK/SOOP + 한국어 자막 + 쇼츠"를 끝까지 이어 주는 오픈소스는 비어 있고, 한국어 반응 어휘(ㅋㅋ, ㄷㄷ 등)로 하이라이트를 검출한 사례는 ClipRadar가 거의 유일하다. 네 번째는 **신호와 규칙의 빈칸**이다. 슈퍼챗·멤버십 급증을 하이라이트 신호로 쓰는 OSS가 없다. Holodex의 클립↔원본 연결과 heatmap을 약한 라벨로 써서 검출기를 평가한 사례도 없다. 기획사 가이드라인을 업로드 직전에 자동 검사하는 도구 역시 없다. 마지막으로 **검증 자료의 빈칸**이 있다. 게임 소리와 BGM이 섞인 일본어 라이브 방송을 놓고 Whisper large-v3, kotoba-whisper, SenseVoice, Qwen3-ASR을 비교한 벤치마크가 없다. 구석에 작게 압축된 Live2D 아바타 프레임에서 애니메 얼굴 검출기를 비교한 벤치마크도 없다. stream2clip이 초기에 자체 평가셋을 만들어야 하는 이유다.

## 조사 방법과 한계: 숫자는 근사치, 판단은 README 기준

GitHub ★ 수, 라이선스, 마지막 push 날짜는 모두 **2026-11-18 기준 근사치**다. 쇼츠·키리누키·Live2D 노트는 GitHub REST/search API를 썼다. 렌더링·3D·기타 노트는 GitHub API가 막혀 미러인 ungh.cc와 LICENSE 원문(raw.githubusercontent, jsDelivr)으로 확인했다. 그래서 **세 노트에서는 "archived" 플래그를 직접 확인할 수 없었다.** 거기서 "정체"는 push 날짜로, "중단"은 README 공지로 판단한 것이다. 노트 사이에 상충하는 정보도 있다. stable-ts는 01 노트에서 ARCHIVED("development paused")인데 06 노트에서는 2026-05 push가 기록돼 있다. Ikaros-521/AI-Vtuber는 04 노트의 검색에는 나오지 않았지만 06 노트에서는 ★4.6k·활발로 확인됐다. VRM Add-on for Blender는 한 노트에서 MIT로, 다른 노트에서 루트 LICENSE 미발견으로 기록됐다. 다음 항목은 **미검증**으로 남는다. MoneyPrinterTurbo의 144k★(비정상적으로 높음), mutonby/openshorts 원본 저장소가 응답하지 않은 이유, OpusClip의 일본어·한국어 지원 여부(홈페이지와 변경 이력이 서로 다름), YouTube 업로드 쿼터 변경 시점, Cubism 5.3 WebM의 알파 지원, Expandable Application의 정확한 정의, HY-Motion 1.0 LICENSE 원문, See-through 가중치 라이선스, SoulX-FlashHead·CartoonAlive·Bunraku의 코드 공개 여부, LivePortrait의 InsightFace 비상업 조건(2차 출처)이다. 모든 기능 설명은 README와 공식 문서에서 가져왔다. 출력 품질이나 VTuber 영상에서의 적합성은 실제로 돌려 보지 않았다. 분야별 전체 목록, 상충 근거, 세부 Gap은 `research_notes/버튜버 영상 작업 프로젝트 레퍼런스/`의 01~06 노트에 그대로 남아 있다.

## 결론

조사 전에는 "참고할 VTuber 클립 도구가 많을 것"이라는 가정이 자연스러웠다. 실제로 나타난 지형은 다르다. 부품은 넘치고 조립품은 비어 있다. 이는 stream2clip의 전략을 바꾼다. 경쟁 상대는 기존 VTuber 도구가 아니다. "실사 얼굴 기준으로 만든 범용 클리퍼를 VTuber에 억지로 맞춰 쓰는 현 관행"이다. 따라서 첫 번째 차별점은 화려한 AI 생성이 아니다. 애니메 얼굴 검출로 아바타 박스를 잡는 레이아웃 엔진, 그리고 OBS에서 알파 아바타 레이어를 따로 받는 입력 경로처럼 지루하지만 아무도 하지 않은 부분이다. 재렌더링도 "AI로 다시 그리기"보다 "방송 중 파라미터를 녹화했다가 결정론적으로 다시 그리기"가 품질, 충실도, 라이선스 모든 면에서 앞선다.

두 번째 함의는 라이선스와 권리가 부가 기능이 아니라 아키텍처 결정이라는 점이다. Live2D Cubism Core의 Expandable Application 조항은 Live2D 백엔드를 플러그인 인터페이스 뒤로 격리하게 만든다. AGPL 클리퍼와 YOLO는 코드 대신 파라미터만 빌리게 만든다. Hunyuan3D의 한국 제외 조항은 한국 사업자의 모델 선택지를 직접 줄인다. 한편 VRM 1.0 meta와 기획사 가이드라인은 기계가 검사할 수 있는 규칙으로 정리할 수 있다. 그래서 "권리를 자동 확인하는 클립 도구"는 방어 수단이면서 판매 포인트가 된다. 특히 한국 기획사 가이드라인과 CHZZK/SOOP 지원이 비어 있다는 점은, 일본 중심의 기존 생태계에서 stream2clip이 가장 먼저 자리 잡을 수 있는 곳이 한국 시장임을 시사한다.
